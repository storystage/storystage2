# WP24.2: Where a pupil's work lives between lessons

- **Status:** proposed by S8, 8 Nov 2026, for the owner to decide. Workplan 24.2: decide before save and open (8.4) is built, which S4 starts next.
- **Feeds:** 8.4 (S4: save, open, autosave), 24.4 (S8: class and pupil separation), the DPIA (D, 17.3), and threat model section 5 ("pupil separation ... waits for WP24.2").
- **Checked against:** the TR1 lessons and IT managers (1.11) when they happen. Section 6 lists which answers would change the recommendation.

## 1. The problem

The done-when for WP24: *in a test with 30 devices, every pupil reopens their own production next lesson and no one else's.* Three things make that hard:

1. **Devices are shared.** A class set of iPads or Chromebooks serves several classes, often with no sign-in at all.
2. **A pupil may not get the same device next week.** Unless the school numbers devices and hands them out the same way, work kept on "the device" is on the wrong one.
3. **The rules.** No StoryStage server and no StoryStage accounts (rule 2). Children's data falls under UK GDPR and the ICO Children's code. Anything adding a third party goes in the DPIA (17.3).

What's at risk: a pupil can't find last week's work (a lost lesson), or a pupil opens, changes or deletes another pupil's film (a privacy breach, and upsetting). Productions hold a pupil's own writing, script and sketches, and their name in the credits. They never hold audio, pictures from the camera, or the key (spec 03 section 1.1).

## 3. Recommendation: A, on top of B wherever the device has it, with C for moving work

1. **Pupil folders in the app (A) by default.** It is the one option that works on every device, including the hardest case, a shared iPad with no sign-in, offline, with nothing new in the DPIA. The teacher adds the class once (screen 11), and each pupil taps their own name, with an optional picture, to open their folder. Autosave keeps work there.
2. **Folders live inside the operating system user's own app data,** so where a school does have per-pupil sign-in (B), the operating system keeps pupils apart as well. Nothing to choose: it happens.
3. **Moving work between devices goes through files (C).** The teacher can **Collect** a class's work into a folder (on the device, a school drive, OneDrive or Google Drive, through the system's picker), and **Hand back** from one. A pupil can **Save a copy to** and **Open** a file in the same way. It's the same `.storystage` file, the same import checks (spec 15 section 3), and no sign-in in StoryStage.
4. **No signed-in cloud saving (D) in the first release.** 8.5 stays off and unbuilt until a school asks and the DPIA can carry it.

**The weak point is a pupil moving to another device.** If devices are numbered and pupils get the same one, A alone is enough. If not, the teacher collects and hands back, which is an extra step each lesson. The TR1 lessons (1.11) should show which is normal. If neither works for schools, C becomes the main route rather than a side one.

## 4. How far pupil folders keep pupils apart

On iPad and Android, an app's data can't be browsed by its user: there is no file manager into it. So a pupil can only reach another's work through StoryStage itself. On a shared Windows or Mac login, a pupil who knows where to look can find the files on disk.

So folders protect against slips and casual looking: opening the wrong folder, or wandering into a friend's. They don't protect against a pupil who sets out to read another's work on a shared desktop login. That matches what StoryStage holds (no audio, camera pictures or key), but it should be said plainly to schools and in the DPIA.

A pupil-chosen picture password could raise the bar inside the app. I don't recommend it for the first release: young pupils forget them, and a forgotten one means a lost film unless the teacher can reset it. **The teacher can always open, move or delete any pupil's folder.**

## 5. Threat model rows (for spec 15 section 2, when this is decided)

| Id | Class | Threat | Control | Test |
|---|---|---|---|---|
| PS1 | I, T | A pupil opens, changes or deletes another pupil's production in the app | Each pupil's folder opens only by choosing that name. Nothing lists other pupils' productions. Deleting asks first, and goes to a bin the teacher can empty | A pupil's view shows only their own productions |
| PS2 | I | A pupil reads another's files on disk, on a shared desktop login | Accepted on shared desktop logins (section 4), and said in the DPIA. Separate OS sign-in (B) removes it | n/a |
| PS3 | I | The class list on a device names children | Names stay on the device, in the app's data, never in a production, an export or a study log. The teacher can use first names or a word and a picture | A production, an export and a study log hold no class list |
| PS4 | D | Work is lost: a device is reset, or a pupil is on another device | Autosave and backups (8.4). Collect and hand back (section 3). Settings tells the teacher when work was last collected | Collect, reset, hand back: every production returns |
| PS5 | T, E | A handed-back file is crafted | The same import rules as any file (spec 15 section 3, F1 to F12) | The hostile-file set, through hand-back |
| PS6 | I | A collected folder on a school drive is readable by others | It's in the school's storage, under the school's sharing settings. The teacher's guide (24.7) says to collect into a staff-only folder | The guide, in 24.7 |

## 6. What the TR1 lessons and IT managers (1.11) should settle

From `docs/spikes/classroom-questions.md`:
- **A4, B2:** are devices shared between classes, and wiped between users? That decides how often A's folders fill up, and whether they survive.
- **A5, B10:** where does work go today, and where would the IT manager want it? A strong "school drive" or "OneDrive" answer makes C the main route.
- **B9:** do pupils have school Google or Microsoft accounts, signed in on the device? If most do, B already separates them, and A becomes a fallback.
- **Not asked yet, and worth adding:** *Does a pupil get the same device each lesson?* That's the weak point in section 3.

## 7. For the owner to decide

1. The default: **A on B, with C for moving work** (recommended), or C as the main route, or one alone.
2. Whether signed-in cloud saving (D, 8.5) is left out of the first release (recommended).
3. Whether to decide now and confirm after 1.11, so S4 can build 8.4 against it (recommended), or wait for 1.11.

## 8. What each option changes for others

- **S4 (8.4):** with A, save and open take a pupil's folder as the place autosave writes, and the production list is per folder. With C, the system file dialogs, already planned. The `.storystage` format doesn't change.
- **S5:** screen 11's **Pupils and folders**, plus a name picker at the start of a lesson, and **Collect** and **Hand back** in Settings.
- **S8 (24.4):** the folders' storage and separation, Collect and Hand back, and the rows in section 5.
- **D (17.3):** the class list on the device (names, and pictures if chosen), what's said about section 4, and nothing new for C.
