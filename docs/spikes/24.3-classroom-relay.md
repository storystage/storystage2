# Spike 24.3: how the Prompter reaches a class

- **Workplan:** 24.3 (decide at M1, after the classroom ground truth in 1.11). C prototypes A and B; the owner decides.
- **Lane:** S8
- **Status:** the probe is built and passes in CI over loopback. **The network test needs the owner, on a real school network** (section 5). Nothing here is decided yet.
- **Code:** `spikes/24.3-relay` (`relay-probe`), built by the `Spikes` workflow, which keeps Windows and macOS binaries for 90 days.

## 1. The question

The Prompter needs a Claude key, which belongs to an adult (0022, 0056) and is never stored in a settings file (CLAUDE.md rule 1). How does a whole class reach it?

| | A. The adult's own key | B. A classroom relay | C. A key on every device |
|---|---|---|---|
| **How** | The Prompter runs where an adult owns the key: a club leader's laptop, a teacher with a small group, a parent at home | The teacher's StoryStage app holds the one key. Pupils' apps reach it over the school network with a class code | Device management pushes the key to every device |
| **Built?** | Yes: the key dialog, gate and transport (WP15k), and per-pupil caps (24.5) | No. Section 3 is the design | No |
| **What the school needs** | Nothing | Devices that can reach each other on the Wi-Fi, a firewall rule for the app, and the teacher's laptop awake for the lesson | Device management that can push a secret |
| **Who sees use** | The adult, on their device (24.5) | The teacher, live, for the whole class | Nobody in one place |
| **Fits the rules?** | Yes | Yes: the key stays on the teacher's device, and every request is checked there | **No**: it puts the key in a settings file on every pupil's device |
| **Main risk** | One key per adult: a class of 30 needs the teacher's own device in reach of every pupil | School Wi-Fi often keeps devices apart (client isolation). Unknown until measured | The rule it breaks |

**C is ruled out** by the decision never to store the key in a settings file. **A** is the pilot's default (24.3). **B** is the only way a whole class gets the Prompter with one key and no StoryStage server, if the network allows it. That's what this spike measures.

## 2. What decides B

1. **Can a pupil's device open a connection to the teacher's?** Many school networks isolate wireless clients from each other, and Windows treats an unknown network as Public, which blocks incoming connections. Only a real school network answers this. The probe measures it (section 4).
2. **How does a pupil's device find the teacher's?** Broadcast and multicast discovery (mDNS, as AirDrop and printers use) are the first things school networks block. So B shouldn't rely on them. A **class code** on the teacher's screen carries the teacher's device's address, a port and a secret, typed or scanned once per lesson. The probe uses one, and also checks whether broadcast happens to work.
3. **Is the link fast and steady enough** for a streamed reply? A reply is a stream of small events over 10–60 seconds. The probe measures the round trip, the worst gap between events sent every 20 ms, and the speed for a megabyte.

## 3. Option B's design, if the network allows it

- **The teacher's device** runs the relay inside StoryStage: the key, the gate and the transport, exactly as now (spec 05 §2). Pupils' devices send `PrompterRequest`s, and the teacher's device checks each one against the pins before the key is read. So a pupil's device can't send anything the Prompter itself wouldn't, and no key is ever on a pupil's device.
- **The class code** is shown on the teacher's screen as letters and a QR code. The probe's code is 20 characters with a 48-bit secret, enough for the test. A real relay would put a 128-bit secret and the fingerprint of the teacher's device's certificate in the QR code, with a shorter typed fallback.
- **Encrypted, both ways proved.** Pupils' requests carry their own writing, so they can't cross the school Wi-Fi in clear. The real relay would use TLS, with the teacher's certificate pinned by the fingerprint in the code, and each pupil's device proving the secret. The probe proves both sides with an HMAC challenge, so the secret is never sent, but it doesn't encrypt: it only measures the network.
- **Caps on the teacher's device:** each pupil's daily cap as now (24.5), counted by the pupil's id from the session. A per-minute limit becomes per pupil, plus one for the class, set under the key's rate limits on the Anthropic account. A class-wide total would need its own error code and words for the learner (S7, 8 Nov).
- **Monitoring:** the teacher's usage view becomes live for the whole class. It would show counts and levels, not what pupils asked, unless the school decides otherwise in the DPIA.
- **Policy:** a pupil's device uses the relay only where its own policy allows the Prompter. A new key, perhaps `prompter.relay`, would let a school switch the relay off.

### Which devices could take part

| Device | As the teacher's (the relay) | As a pupil's |
|---|---|---|
| Windows or Mac laptop | **Yes**, if it stays awake and IT allows the app through the firewall on the school network | Yes |
| iPad | **Not practical**: iPadOS suspends an app in the background, so the relay would stop whenever the teacher switched app | Likely. iPadOS asks once for permission to use the local network; whether device management can grant that ahead of time needs checking on a managed iPad |
| Android or Chromebook (the Android app) | **Unlikely**: on a Chromebook the Android app sits behind its own address translation, so other devices can't reach it. To check on a device | Likely: outgoing connections work |
| Browser version | No | **No**: an https page can't open plain connections to a device on the local network (mixed content), Chrome also blocks public sites reaching private addresses, and no device on a school network can have a publicly trusted certificate |

So B needs **the teacher on a laptop**, and pupils on the apps.

## 4. The probe

`relay-probe listen` on the teacher's device shows a class code. `relay-probe connect <code>` on a pupil's device then does the following, and prints the results in plain words with a one-line verdict:

1. **Broadcast:** asks the network, without the code, whether a teacher's device is listening.
2. **Connect:** opens a connection to the address in the code, with a 5-second limit.
3. **Prove:** the teacher's device sends a random challenge; the pupil's device answers with an HMAC of it under the secret; the teacher's device answers back. A wrong code is turned away.
4. **Echo:** 20 round trips of one byte. Gives the typical and worst.
5. **Reply-like events:** 50 small messages sent 20 ms apart. Gives the longest wait between them.
6. **Bulk:** 1 MB at full speed. Gives Mbit/s.

The teacher's device reports each pupil's device that tried, and whether it proved the code. Nothing is sent anywhere else, and nothing is kept. CI runs the tests and a trial over loopback on Windows, macOS and Linux: a right code finishes, and a wrong one is turned away.

### Results in CI (8 Nov 2026, loopback on one runner)

| Runner | Right code | Wrong code | Round trip | Worst event gap (sent every 20 ms) | 1 MB |
|---|---|---|---|---|---|
| Linux | finished | turned away | under 0.1 ms | 20.3 ms | 400.6 Mbit/s |
| Windows | finished | turned away | under 0.1 ms | 20.7 ms | 406.0 Mbit/s |
| macOS | finished | turned away | 0.1 ms | 105.1 ms | 225.9 Mbit/s |

Loopback only shows the probe works: it says nothing about a school network. The macOS runner's one 105 ms gap is most likely its scheduler on a shared machine, since nothing crossed a network; the owner's test will show whether gaps like it happen between real devices.

## 5. The owner's test

1. From the latest **Spikes** run on this branch, download `relay-probe-Windows` and `relay-probe-macOS` (Actions, the run, Artifacts).
2. On the **teacher's laptop**, on the school's Wi-Fi as a teacher would use it, run `relay-probe listen`. If Windows asks whether to allow it, allow it on **private** networks, and note whether a teacher's own account could do that, or IT had to.
3. On **two or three other laptops** on the same Wi-Fi, as pupils' devices would join it, run `relay-probe connect <code>` with the code from step 2.
4. Repeat with the teacher's laptop on the **staff** network or a cable, and the others on the **pupils'** network, as a real lesson might.
5. Fill in the table, and ask the IT manager whether client isolation is on, and whether the firewall is managed.

| School | Network(s) | Broadcast found it? | Reached it? | Proved? | Round trip | Worst event gap | Speed | Firewall: who allowed it? |
|---|---|---|---|---|---|---|---|---|
| | | | | | | | | |

**Reading the results:**
- "Reached it" **no** on the pupils' network means B needs IT to change the network, which most schools won't for one app. Then A for the pilot, and B only where a school can allow it.
- "Reached it" **yes**, with a round trip under about 50 ms and no event gap over about 500 ms, means B could work there.

## 6. Proposed

- **For the pilot: A** (already built), as the workplan expects.
- **Run the probe at the 1.11 school visits** with the IT managers' questions (`classroom-questions.md`, question 6), and decide B at M1 on what it finds.
- **If B goes ahead:** build it as in section 3. It would be the relay in Rust on the teacher's device, behind the existing transport. A pupil's device would get a relay transport in `@storystage/host`, so the studio wouldn't change. It also needs TLS with a pinned certificate, the class code and QR, per-pupil and class-wide caps with their own error code, the live usage view, `prompter.relay`, and DPIA rows for prompts crossing the school network. About three weeks.
- **C stays ruled out.**
